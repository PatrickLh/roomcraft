# RoomCraft V1.0 产品决策记录（PRD）

> 生成方式：/grilling 逐项质询确认，共 18 个决策点。日期：2026-10-08。

## 1. 项目定位

- **性质**：创业/产品 MVP，探索后续商业体系。
- **一句话**：装修业主上传户型图 → AI 识别生成可编辑 3D 户型 → 俯视编辑家具、3D 实时观察 → 上传风格案例生成写实效果图。
- **一句话定位的差异化**：酷家乐要求手动画墙/导入 CAD，普通业主做不到；本产品"上传截图就出 3D"。

## 2. 目标用户与商业化路线

| 阶段 | 用户 | 角色 |
|---|---|---|
| **V1（MVP）** | 装修业主（C 端） | 唯一交互对象 |
| 后续 | 室内设计师（B 端） | 变现逻辑，V1 不做交互，架构不堵死 |
| 后续 | 家具电商导购（D 端） | 变现逻辑；模型元数据（品类/尺寸/风格标签）从 V1 起预留 SKU 检索地基 |

## 3. 核心架构（全项目最重要的单一决策）

**大模型只当"读图员"，3D 由代码确定性生成。**

```
户型图片 → 视觉大模型 → 户型 JSON（墙/门/窗/房间标签/尺寸标注）
                              ↓
                Three.js 程序化建模（拉伸墙体、开洞、放家具）
                              ↓
              俯视编辑（可旋转） ⇄ 3D 行走视角实时联动
                              ↓
        效果图 = 3D 场景截图 + 风格参考图 → 商用生图 API → 写实效果图
```

- 拒绝生成式 3D（图生 mesh）：不可编辑，与核心编辑需求根本冲突。
- 效果图走 **2a 路线（生成 2D 效果图）**，"3D 是工作台，效果图是梦"的风格落差可接受。
- 结构化 JSON 是一切的地基：渲染、编辑、存档、B/D 变现都依赖它。

## 4. 功能范围

### 4.1 户型图识别管线

- **输入**：仅图片（JPG/PNG/WebP），两类：① 电子户型图（开发商宣传图，最规整）；② 手机翻拍/截图。**拒收 CAD/DWG/DXF/PDF 矢量**。
- **识别元素**：仅四类——**墙体、门、窗、房间名标签**。其余降级或忽略：飘窗→墙+窗、柱子→忽略、阳台→普通房间+落地窗、楼梯→忽略并提示"复式暂不支持"。
- **比例尺标定**：完全依赖大模型读图上尺寸标注（多条标注交叉验证取一致方案），失败 → 提示重试。"点墙输入真实长度"的兜底交互列入 **V1.1 首批项**（已知风险，见 §11）。
- **修正能力**：轻量墙体修正模式（俯视 2D 下）：拖动墙端点、删墙、两点间加直墙、开关门窗洞。不做完整户型绘制编辑器。与家具编辑共用拖拽/吸附/undo 基础设施。

### 4.2 3D 呈现与双视角

- 俯视模式：可旋转角度，编辑模式下操作家具与墙体。
- 3D 模式：行走视角观察。
- 俯视 ⇄ 3D 平滑切换，编辑即所见（编辑时同步观察 3D 效果）。
- 默认层高、材质等渲染参数在设计稿阶段定，此处不锁死。

### 4.3 编辑模式（产品原则：真实尺寸是卖点）

**有**：拖拽移动（网格吸附 + 贴墙吸附）、旋转（90° 步进默认，可切自由）、删除、复制、从品类目录添加、undo/redo。

**没有**：
- ❌ 自由缩放（破坏尺寸真实性，商业自毁）
- ❌ 碰撞硬阻止（重叠时高亮警告，用户自己决定）
- ❌ 堵门检测（V1 不做）

### 4.4 风格效果图（能力 2a，商业验证核心）

- 管线：用户选机位 → Three.js 渲染场景截图 → 截图 + 风格参考图 → 商用生图 API（字节 Seedream / 阿里通义万相档位，参考图生图模式）→ 写实效果图。
- 机位：V1 提供 3–4 个自动预设机位（房间中心 + 朝向启发式）；自由摆相机 V2。
- 深度图控制（ControlNet 式锁布局）留 V2；渲染深度图的管线提前埋好。
- **AI 生成标识水印从第一行代码就带**（显式水印 + 隐式元数据，见 §7）。
- 明确不做：2b 路线（把风格实时应用到可编辑 3D 场景）。

### 4.5 家具模型

- **V1**：精选 CC0 低多边形模型库（poly.pizza / Quaternius / Kenney），50–80 件高频品类（沙发/床/餐桌/衣柜/书桌/家电）。
- **美术方向**：清新低多边形（统一风格 = 设计感；写实无 PBR 会显廉价）。
- **模型源是可插拔数据层**：场景引用模型 ID + 元数据，不绑死库；后续可切"Codex + Blender（bpy）参数化生成"路线。

## 5. 账号与配额

- **游客漏斗**：游客无需注册走完全流程（方案存本地）；点"保存方案"时才登录（V1 手机验证码；微信扫码待企业资质）。
- 登录后：方案云存、"我的方案"列表、只读分享链接（传播回路）。
- **配额（AI 调用限制）**：

| 维度 | 户型解析 | 效果图生成 |
|---|---|---|
| 游客（设备指纹 + IP 双维，每日） | 3 次 | 3 张 |
| 注册用户（按账号，每日） | 5 次 | 10 张 |

- 计数走后端 DB；解析失败不扣次数；生图失败自动重试一次且不扣。
- 超限提示"明日恢复，注册得更多额度"。V1 不做支付，付费额度包 V1.x。
- AI 的 API Key 一律不落浏览器，全部走后端代理（代理层同时做频控配额 = 计费系统雏形）。

## 6. 技术栈与工程架构

- **前端**：Vue 3 + TS + Vite + Pinia + Three.js（原生 + 自建场景管理层，不用包装层）+ Element Plus（仅表单/弹窗，画布完全自定义）。
- **后端**：Python + FastAPI + Pydantic + PostgreSQL（方案存 JSONB）。选 Python 的理由：agent 编排生态（LangGraph / pydantic-ai）、将来自建推理（ControlNet/深度估计）、**Blender 自动化即 Python（bpy）**。
- **Schema 共享**：户型 JSON Schema 为唯一事实源 → 前端 `json-schema-to-typescript` 生成 TS 类型，后端生成 Pydantic 模型，CI 用同一组 fixture 双向校验防漂移。
- **存储**：阿里云 OSS（上传图 + 效果图）。
- **AI Provider 适配层**：视觉大模型与生图 API 均可插拔，Provider + API Key 走配置（环境变量/管理后台），用户自行配置模型与密钥。
- **仓库**：pnpm workspace monorepo（`apps/web` + `apps/server` + `packages/shared-schema`）。

## 7. 合规

- **ICP 备案**：开发期间并行启动，不阻塞开发。
- **AI 生成内容标识**：按《人工智能生成合成内容标识办法》（2025-09 生效），效果图带显式水印 + 隐式元数据标识，第一天就实现。
- **私域内测先行**：邀请码/私密分享链接小范围验证（业主群），降低合规暴露面。
- **算法/深度合成备案**：PMF 信号出现、准备公开推广时启动。
- 隐私政策 + 用户协议：模板先上。

## 8. 里程碑

| 阶段 | 内容 | 出口标准 |
|---|---|---|
| **M0**（1–2 周） | monorepo 脚手架；**Spike A**：10 张真实户型图跑视觉大模型，人工评估 JSON 准确率；**Spike B**：假场景渲染图 + 风格图调生图 API 看布局保持；Three.js 假户型 JSON → 双视角切换跑通 | 两大不确定性有真实答案 |
| **M1** 核心闭环 | 上传 → 解析 → 校验入库 → 3D 呈现 + 失败重试；AI 适配层 + 配额上线 | 自己的户型图能看到 3D |
| **M2** 编辑器 | 俯视墙修正、家具增删改/吸附/undo、双视角联动、账号 + 保存 + 分享链接 | 内测用户能完整"改" |
| **M3** 效果图 | 预设机位、生图管线、AI 水印、效果图历史 | 效果图能看、能存、能分享 |
| **M4** 内测 | 漏斗埋点、邀请码、移动端"可看"、性能优化、业主群投放 | 30–50 真实业主进来自由使用 |

原则：先让**看**成立，再让**改**成立，再让**美**成立，最后让**传**成立；最大不确定性（解析准确率、生图布局保持）在 M0 用裸验证杀掉，不写一行产品代码。

## 9. 验证标准（V1 的"做完"≠"验证过"）

**质量线（产品成立）：**
- 电子户型图解析结构可用率 ≥ 80%（Spike A 先行给答案）
- 效果图布局保持 + 风格还原主观可用率 ≥ 60%
- 上传 → 看到 3D，P50 ≤ 60s

**价值线（商业假设成立，内测 30–50 真实装修业主）：**
- 漏斗：上传 → 看到 3D ≥ 70%；看到 3D → 生成 ≥1 张效果图 ≥ 50%；生成 → **主动分享 ≥ 30%**
- 次周回访留存 ≥ 20%
- **北极星指标：分享次数 / 激活用户**

**触发器**：价值线达标 → 加注公开版 + 付费包；质量线不达标 → 回到 Spike A 换模型/prompt 策略，不堆功能。

## 11. 已知风险登记

| 风险 | 影响 | 对策 |
|---|---|---|
| 无尺寸标注的翻拍图解析失败 | 部分用户 V1 直接失败 | V1.1 首批做"点墙标定"兜底（只加交互，不动架构） |
| Spike A 解析准确率不达标 | 核心闭环不成立 | M0 第一周即知；换模型/拆步骤（先轮廓后语义）/换 prompt 策略 |
| Spike B 生图布局保持差 | 商业验证点失真 | M0 即知；升级深度图控制（V2 提前）或换 API |
| 解析耗时超 60s | 漏斗第一格流失 | 异步任务 + 进度反馈（SSE/轮询），M1 起监控 P50 |
